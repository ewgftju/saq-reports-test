`received-schemas.js` и `professional-schemas.js` содержат только разрешенные структурные ячейки. Скрипты `scripts/extract-received-forms.py` и `scripts/extract-professional-forms.py` читают предоставленные файлы, но не переносят строки организаций, адреса, БИН, ФИО и формулы источника. В исходной форме ОПИ повреждены итоговые ссылки; в приложении итоги пересчитываются только по числовым показателям.

`received-engine.js` использует явные факты плана (`plan.year`, `quarter`, `coverage`, даты назначения/завершения/исключения), решения по поручениям и заключения контроля качества. Плановый охват не подменяется фактическим. Год плана определяется датой «по», события учитываются на эту дату. Фактический квартал исполнения определяется завершением. Квартальные количества и охват сводной пока считаются по АС и АФО вместе; это принятое допущение для неоднозначной шапки без формул. Доля электронного аудита считается от всех аудитов, отклонение от 29% — в процентных пунктах, суммы нарушений — по электронным аудитам.

`professional-engine.js` принимает явный объект `record.professional`: категорию субъекта, включение и состояние исполнения перечня, требования, реквизиты уведомления/предписания/ответов, отдельные денежные меры, административные факты и двуязычные поля. Категории АО/ОПИ не выводятся из названия или общего статуса. Справочник КоАП воспроизводит предоставленный образец и не является проверкой актуальности законодательства. Для сравнения используются те же даты прошлого года, денежные значения в тыс. тенге переводятся в млн. При нулевой базе процент изменения отсутствует.

Дополнительные факты и записи 2025 года из `*-demo-data.js` вымышлены и применяются только к штатному учебному набору. При передаче собственных записей неизвестные показатели остаются «Нет данных», а не заполняются демонстрационными значениями. Рабочие API не подключены. Правило формирования и единицы измерения сохраняются на листе «Параметры» Excel.

## Контракт текущего макета

`engine.generate(records, config)` принимает нормализованные записи и конфигурацию. `config` содержит `sources`, `filters`, `columns`, `group`, `name`, `template`. Результат содержит строки, перечень колонок, параметры, дату формирования, число записей и уникальных объектов. Это локальный контракт макета, а не существующий API модулей.

В рабочем модуле нужен серверный сервис формирования. Клиент отправляет конфигурацию, сервер проверяет допустимые поля и права пользователя, читает согласованную версию данных и возвращает результат либо идентификатор фонового задания. Экспорт должен строиться по тому же снимку, что и предпросмотр. Ограничения доступа нельзя доверять клиентским фильтрам.

## Единицы учета

| Источник | Ключ и единица | Основные данные |
| --- | --- | --- |
| СУР | risk_assessment_id + версия расчета + объект | Балл, уровень риска, период, отбор |
| ВГА | case_id; отдельно audit_object_id | Дело, объект, охват, отчетная дата, нарушения |
| СВА | case_id; отдельно audit_object_id | Мероприятие, объекты, результаты, исполнение |
| ПРОФ | control_case_id + object_id | Акт результатов, предписания, подтвержденные меры |
| Возражения | objection_id; пункты отдельно | Связанное дело/акт, оспоренный пункт, решение |

Демо использует одну строку на запись модуля с одним объектом. Рабочие данные требуют отдельных фактов: дела, объекты, нарушения, исполнение, санкции и бюджетные программы. Плоское объединение этих таблиц до суммирования приведет к повторному учету. Сначала агрегировать каждую таблицу на нужном уровне, затем соединять по явным ключам. Уникальный ключ записи макета — `(module, id)`, уникальный объект — БИН.

## Привязка полей исходных форм

Четыре схемы и полный путь каждого заголовка находятся в `templates.js`. Начальное сопоставление демонстрационных полей находится в `engine.templateMapping()`. Для рабочей реализации создать версионируемый каталог показателей: код, подпись, единица, модуль, документ/поле, ключ факта, дата учета, формула, допустимая агрегация, правило пустого значения, дата начала действия.

Требуют согласования: классификатор нарушений по разделам/главам/принципам; бюджетные средства и активы; закупочные процедуры и лоты; восстановление/возмещение/отражение по учету; рекомендации; передачи материалов; административные и дисциплинарные взыскания. Часть этих источников может находиться за пределами пяти модулей. Наличие формы само по себе не означает наличие всех показателей в системе.

Форма АБП должна формироваться на уровне объекта риска, АБП, программы и подпрограммы, с распределением денежных сумм по этому уровню. Демо имеет один АБП и одну программу на запись. Исходный пример 30301 содержит несколько строк одного дела: суммировать повторяющийся охват дела в каждой строке нельзя.

ЭГА рассматривается как электронный формат ВГА в соответствии с архитектурой SAQ. Перед рабочим подключением подтвердить признаки отбора с владельцем формы. Свод по органам в демо использует дела ВГА, как указано в исходном заголовке «Количество дел ВГА»; добавление СВА и ПРОФ в официальный свод требует отдельной методики.

## Периоды и итоги

- В демо период — отчетная дата включительно. Период охвата аудита, дата утверждения и дата исполнения являются отдельными измерениями.
- Просрочка — незавершенная запись со сроком ранее конца выбранного периода. Рабочее восстановление исторического статуса потребует истории событий; текущий статус не доказывает статус в прошлом.
- Денежные значения: тысячи тенге. Для рабочего сервиса использовать decimal, округление на выходе по согласованной точности.
- Балл риска — среднее по выбранным расчетам. Финансовые показатели неприменимы к СУР и возражениям.
- Возражения не увеличивают сумму нарушений; окончательное решение должно изменять согласованную версию нарушения. Нельзя одновременно суммировать исходную и скорректированную версии.
- Процент устранения — сумма подтвержденных мер / сумма, подлежащая устранению. При нулевом или отсутствующем знаменателе значение отсутствует.
- Суммирование уникальных объектов по модулям недопустимо: один БИН может встречаться в разных модулях.

## Приемка интеграции

Сверить с владельцем отчета закрытый контрольный период по каждой форме. Проверить отдельное дело с несколькими объектами и программами, несколько нарушений и исполнений одного предписания, возражение с частичной отменой, записи на границе периода, нулевые/отсутствующие значения и права территориальных пользователей. Итоги предпросмотра и выгрузки должны совпадать на одном снимке.

## Пример связанного набора (18.10.2026)

`linked-data.js` — изолированные вымышленные факты, не копии рабочих записей. `joinAuditFacts(facts, asOf)` агрегирует нарушения и подтверждённые исполнения/отмены отдельно, затем выдаёт одну строку на дело ВГА. `assessmentId` связывает конкретный расчёт СУР, `sourceModule + caseId` — возражения, `violationId` — денежные операции. БИН используется для объекта, не для соединения всех дел.

Конфигурация `dataset: case-links` выбирает этот набор в `generate()`. Период отбирает дела по дате; связанные факты учитываются накопительно по дату окончания с проверкой даты подтверждения. Это пример методики, не утверждённая методика официальной формы «Остатки».

Первое дело: нарушения 1000 + 500, исполнения 100 + 200 + 200, два возражения, одна подтверждённая отмена 200. Остаток 1500 − 500 − 200 = 800 тыс. тенге. Операция на проверке и операции после даты среза исключаются. Дубликаты идентичного ID устраняются, конфликтующие версии и отрицательный остаток вызывают ошибку.

В производстве нужны серверные витрины по разрешённым наборам и версиям. API получает ID набора, поля, период, фильтры, группировку; не произвольный SQL/ключи от клиента. На сервере проверяются права, полная загрузка источников, версии документов и единицы (ВГА хранит отдельные поля в тенге, текущая отчётность — в тыс. тенге). Для СВА/ПРОФ вводятся собственные составные ключи. Ошибка/недоступность источника не должна превращаться в нулевую сумму.

## Каталог допустимых наборов — 19.10.2026

В конфигурацию добавлен `dataset`: `module`, `registry` либо `case-links`. В старой конфигурации без этого поля один источник трактуется как `module`, несколько — как `registry`.

Клиент не передает произвольные ключи соединения. Каталог должен определять для каждого набора единицу строки, фиксированные/допустимые источники, поля, фильтры, группировки, агрегаты, единицы измерения и правила связи. В текущем демо это `datasetKind`, `availableFields`, `availableFilters`, `availableGroups` и `validate` в `engine.js`.

Для `registry` разрешены общие идентификационные реквизиты и счетчики. Даже если пользователь выбрал только аудитные модули, состав этого набора не расширяется до денежных показателей. Для межмодульного финансового отчета нужен отдельный согласованный набор с методикой учета.

`validate()` отклоняет неизвестные наборы/модули, дубли, чужие поля, несовместимые группировки и активные фильтры, а также исходные Excel-формы вне одиночного модуля. `normalizeBuilderConfig()` применяется только при редактировании или открытии старых настроек: исключает несовместимое с сообщением пользователю. `generate()` ничего не исправляет молча. Исторический результат с несовместимыми настройками не переобозначается как новый набор; требуется повторное формирование.

Эти проверки сейчас выполняются в локальном приложении. Перед подключением рабочих API тот же каталог и правила необходимо проверять на сервере вместе с правами доступа. Ограничение интерфейса не является серверной авторизацией.
